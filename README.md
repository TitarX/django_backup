# Резервное копирование Django и PostgreSQL

`django_pgsql_from.sh` создает резервную копию текущей директории проекта и базы.
`django_pgsql_to.sh` распаковывает ее в текущую директорию и восстанавливает базу.
Скрипты рассчитаны на Bash, GNU tar и клиентские утилиты PostgreSQL.

Настройки задаются переменными окружения или значениями в начале скриптов:

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `DB_NAME` | Исходная или целевая база | `your_db_name` |
| `DB_USER` | Пользователь подключения | `your_db_user` |
| `DB_ROLE` | Роль выполнения команд и владелец восстановленных объектов | `DB_USER` |
| `DB_PASSWORD` | Пароль пользователя подключения | Непустой `PGPASSWORD`, иначе `your_db_password` |
| `DB_HOST` | Сервер или директория Unix-сокета | `127.0.0.1` |
| `DB_PORT` | Порт PostgreSQL | `5432` |
| `ARCHIVE_NAME` | Путь к архиву, его директория должна существовать | `backup.tar.gz` |

Для пароля используются по порядку: непустой `DB_PASSWORD`, непустой
`PGPASSWORD`, значение `your_db_password`. Выбранный пароль передается
утилитам PostgreSQL через `PGPASSWORD`.

Скопируйте скрипт создания копии в корень Django-проекта и запустите оттуда:

```bash
cp /path/to/dumps/django_pgsql_from.sh .
DB_NAME=source_db DB_USER=source_user DB_PASSWORD=source_password \
    bash ./django_pgsql_from.sh
```

Для восстановления перейдите в целевую директорию проекта и скопируйте туда
скрипт и рабочую копию архива. Целевая база и роль должны существовать заранее.
Можно использовать другие имена:

```bash
cp /path/to/dumps/django_pgsql_to.sh .
cp /backups/backup.tar.gz ./backup.tar.gz
DB_NAME=target_db DB_USER=target_user DB_PASSWORD=target_password \
    bash ./django_pgsql_to.sh
```

Если пользователь подключения отличается от владельца объектов, укажите
`DB_USER=restore_login DB_ROLE=target_owner`. Пользователь должен иметь право
`SET ROLE target_owner`, а роль - права создавать объекты в целевой базе и
удалять заменяемые объекты. `--no-owner` не обходит проверку этих прав.

Дамп сохраняется в архиве по пути `db/db_dump.sql`. Несмотря на расширение
`.sql`, это формат PostgreSQL custom (`-Fc`), совместимый с прежними архивами
этих скриптов. Локальная директория `db` используется как временная.
В таком формате `pg_dump --no-owner` игнорируется, поэтому параметр передается
в `pg_restore`. Параметр `--role` выполняет `SET ROLE`, а не переименовывает
старые роли. `--no-acl` исключает восстановление исходных `GRANT`/`REVOKE`.
Отдельные права для дополнительных ролей нужно настроить после восстановления.

Восстановление заменяет файлы проекта и объекты базы, присутствующие в дампе.
Остальные объекты базы сохраняются. База восстанавливается одной транзакцией:
при ошибке изменения базы откатываются, но уже распакованные файлы остаются.
При переносе обновите настройки подключения в Django (`.env` или `settings.py`):
файлы в архиве содержат исходные значения.

В архив не входят директории `venv` и `.venv`, итоговый и временный архивы,
а также файлы с именем запускаемого скрипта (`basename "$0"`).

После успешного выполнения скрипты очищают служебные материалы:

- Создание копии удаляет директорию `db` и файл с именем текущего скрипта.
  Созданный архив остается.
- Восстановление удаляет директорию `db`, входной архив по пути `ARCHIVE_NAME`
  и файл с именем текущего скрипта. Архив удаляется и при указании пути вне
  директории проекта.

Директория `db` удаляется целиком со всем содержимым. Файл скрипта удаляется
по имени из текущей рабочей директории, поэтому примеры используют локальные
копии скриптов. После использования скрипты также выполняют `unset PGPASSWORD`
в своем процессе.

При ошибке скрипты завершаются с ненулевым кодом. Старый архив сохраняется,
пока новый не создан успешно. Если ошибка возникает до финальной очистки,
созданные или распакованные служебные материалы могут остаться на диске.

Справка: [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html),
[pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html).

Сценарий `tests/test_django_pgsql.sh` требует адаптации к текущей автоочистке:
он читает дамп после удаления `db` и повторно использует удаляемый архив.
Для работы сценария нужны серверные утилиты PostgreSQL (`initdb`, `pg_ctl`)
в `PATH` и запуск от обычного пользователя. Он использует отдельный временный
кластер без TCP.
