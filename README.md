# Резервное копирование Django и PostgreSQL

`django_pgsql_from.sh` создает резервную копию текущей директории проекта и базы.
`django_pgsql_to.sh` распаковывает ее в текущую директорию и восстанавливает базу.
Скрипты рассчитаны на Bash, GNU tar и клиентские утилиты PostgreSQL.

Настройки задаются переменными окружения или значениями в начале скриптов:

| Переменная | Назначение | По умолчанию |
| --- | --- | --- |
| `DB_NAME` | Исходная или целевая база | `your_db_name` |
| `DB_USER` | Пользователь подключения | `your_db_user` |
| `DB_ROLE` | Роль выполнения команд и владелец восстановленных объектов | `DB_USER` |
| `DB_PASSWORD` | Пароль пользователя подключения | `PGPASSWORD` или `.pgpass` |
| `DB_HOST` | Сервер или директория Unix-сокета | `localhost` |
| `DB_PORT` | Порт PostgreSQL | `5432` |
| `ARCHIVE_NAME` | Путь к архиву, его директория должна существовать | `backup.tar.gz` |

Запускайте из корня Django-проекта. Пароль можно хранить в `.pgpass`:

```bash
DB_NAME=source_db DB_USER=source_user \
    bash /path/to/dumps/django_pgsql_from.sh
```

Для восстановления перейдите в целевую директорию проекта. Целевая база и роль
должны существовать заранее. Можно использовать другие имена:

```bash
DB_NAME=target_db DB_USER=target_user ARCHIVE_NAME=/backups/backup.tar.gz \
    bash /path/to/dumps/django_pgsql_to.sh
```

Если пользователь подключения отличается от владельца объектов, укажите
`DB_USER=restore_login DB_ROLE=target_owner`. Пользователь должен иметь право
`SET ROLE target_owner`, а роль - права создавать объекты в целевой базе и
удалять заменяемые объекты. `--no-owner` не обходит проверку этих прав.

Дамп находится в `db/db_dump.sql`. Несмотря на расширение `.sql`, это формат
PostgreSQL custom (`-Fc`), совместимый с прежними архивами этих скриптов.
В таком формате `pg_dump --no-owner` игнорируется, поэтому параметр передается
в `pg_restore`. Параметр `--role` выполняет `SET ROLE`, а не переименовывает
старые роли. `--no-acl` исключает восстановление исходных `GRANT`/`REVOKE`.
Отдельные права для дополнительных ролей нужно настроить после восстановления.

Восстановление заменяет файлы проекта и объекты базы, присутствующие в дампе.
Лишние файлы и объекты автоматически не удаляются. База восстанавливается одной
транзакцией: при ошибке изменения базы откатываются, но уже распакованные файлы
остаются. При переносе обновите настройки подключения в Django (`.env` или
`settings.py`): файлы в архиве содержат исходные значения.

При ошибке скрипты завершаются с ненулевым кодом. Старый архив сохраняется,
пока новый не создан успешно. Директории `venv` и `.venv` в архив не входят.

Справка: [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html),
[pg_restore](https://www.postgresql.org/docs/current/app-pgrestore.html).

Интеграционные проверки: `bash /path/to/dumps/tests/test_django_pgsql.sh`.
Нужны серверные утилиты PostgreSQL (`initdb`, `pg_ctl`) в `PATH`. Запускайте
от обычного пользователя. Тест создает отдельный временный кластер без TCP,
проверяет перенос в другую базу и роль, старые архивы и обработку ошибок,
затем удаляет свои временные файлы.
